## 1. What was discovered

`CommitmentPoolingModule` — the single deployed contract assembled from the
`src/modules/pooling/*` linear inheritance chain — compiled to **56,601 bytes** of deployed
bytecode under the production profile (`via_ir`, `optimizer_runs = 1`, the profile
`upgrade.ts` broadcasts with). The EIP-170 limit enforced by Arbitrum One and every
Ethereum-equivalent chain is **24,576 bytes**; the creation transaction would additionally
have exceeded EIP-3860's 49,152-byte initcode cap. **The module could not have been deployed
at all.**

Nothing in the repository could catch this:

- Foundry's test EVM does not enforce EIP-170 — all 1,650+ tests, including the Arbitrum fork
  rehearsal, deployed the oversized artifact without complaint.
- No `forge build --sizes` or equivalent gate existed in any script or workflow.
- The module had never been broadcast to a real network (`deployments/*.json` carries no
  pooling address), so the wall would have surfaced for the first time at Release-phase
  broadcast (due 2026-08-12).

Calibration that made the risk legible: `OctantModule` compiles to 24,486 bytes — **90 bytes
under the limit** — so the codebase had already been surfing this wall without a guard.

## 2. What was built

### 2a. Size gate (now permanent)

`packages/contracts/script/utils/check-contract-sizes.ts`, wired as:

- `bun run check:sizes` (contracts package) / `bun run check:contract-sizes` (root)
- CI: `.github/workflows/contracts.yml` → "Check deployed bytecode sizes (EIP-170)" in the
  Lint And Build job.

It builds the production profile (never with an explicit source path — see §5 gotcha),
measures every concrete deployable under `src/` (excluding `vendor/`, `mocks/`,
`interfaces/`), fails above 24,576 bytes, warns above 90% of the limit, and supports a
`RELEASE_BLOCKER_ALLOWLIST` that must stay empty.

### 2b. Deployed-library architecture

All heavyweight behavior moved out of the module into **deployed external libraries** under
`src/modules/pooling/libraries/`, DELEGATECALLed by thin facet shells. Each library is its own
deployment with its own 24,576-byte budget. The 19-facet linear chain shape is retained
(minus `CommitmentPoolingCreationValidation`, deleted after its validators moved); facets are
now shells that build a value-typed `Env` snapshot (`CommitmentPoolingContextLib.Env` via
`CommitmentPoolingAccess._env()`) and thread explicit storage-mapping references.

**Result: the module is 21,198 bytes deployed — 3,378 bytes under the limit** (was 2.30×
over). Every library sits far under its own budget.

### 2c. The three deliberate pattern deviations

1. **Counter shells** — libraries receive `nextCommitmentId`/`nextCycleId`/
   `nextCommitmentSeriesId`/`nextPoolId` **by value** and the shell increments only when the
   returned id equals the passed value, preserving idempotent replay returns without needing
   scalar storage writes from a library.
2. **Config stays module-side** — measured: extracting the value-typed setters *added*
   160 bytes (boundary codecs exceed the tiny bodies). Recorded in the facet header so nobody
   re-attempts it.
3. **Raw-return view forwarding** — struct/array views (`getCommitment`, `getPool`,
   `getCycle`, `getCommitmentSeries`, `getPendingClaim`, `getRequirement`, `getContributor`,
   `getConfirmers`, `getLinkedWorkUIDs`, `getPoolByGarden`) forward the library's return data
   without decoding/re-encoding, which is what actually evicts the large ABI encoders (the
   40-field `Commitment` above all — worth ~5.3KB). Mechanics: the `view` shell STATICCALLs
   `poolingViewDelegate(bytes)` on the module itself (self-only guard), which DELEGATECALLs
   `CommitmentPoolingViewsLib` and returns the raw bytes; mapping slots are compiler-derived
   via `.slot`, never hand-maintained; each shell ends in an unreachable `revert(0,0)` so the
   compiler emits no phantom default-return encoder. `poolingViewDelegate` is the one
   ABI addition (non-interface, operational plumbing like the OZ/UUPS externals).

### 2d. What did NOT change

- **Storage layout**: byte-identical. Only `CommitmentPoolingStorage` declares state;
  libraries hold none. `bun run check:storage-layout` passes against unchanged baselines.
- **ABI of all 86 interface functions**: signatures, events, errors, and revert data are
  unchanged. `ICommitmentPoolingModule` was not touched. The indexer boundary is unaffected —
  DELEGATECALL emits every event from the proxy address exactly as before.
- **UUPS machinery, initialize semantics, `deployCode` test resolution** (Foundry links
  library addresses in test artifacts automatically), **the deploy/upgrade script path**
  (`new CommitmentPoolingModule()` in `DeployPooling.s.sol`/`Upgrade.s.sol` auto-deploys and
  links the libraries in the same broadcast).

## 4. Deploy-ops implications (follow-ups for the release lane)

- **Broadcast shape**: the pooling deploy now emits ~13 additional CREATE transactions (one
  per deployed library) before the implementation. `forge script` handles ordering and
  linking automatically; gas budgeting for the deploy wallet should account for it.
- **Etherscan verification**: the implementation verifies with library address mappings.
  `forge verify-contract` needs `--libraries` entries (or verify via the standard-json from
  the broadcast). `post-deploy-verify.ts` should learn to check the library addresses too.
- **Upgrades**: a behavior change in any library requires deploying the changed library and a
  new implementation linked against it, then the normal UUPS upgrade. The storage baseline
  keeps protecting the layout; `pooling:upgrade:arbitrum` already runs it.
- **OctantModule is 90 bytes under the limit** (24,486/24,576, production profile). It is
  deployed and functional, but any future Octant edit will trip the WARN band — plan the same
  library treatment before touching it.

## 5. Toolchain gotchas recorded while working

- `forge build <path> --skip test --skip script` under sparse mode has been observed to
  **silently skip emitting the artifact of the named concrete target** (both default and
  production profiles) while compiling its dependencies. The size gate and any measurement
  must run a full `forge build --skip test --skip script` with **no path argument**. Stale
  caches after such runs were cleared with `rm -rf .generated/foundry/cache/<profile>`.
- Foundry's test EVM does not enforce EIP-170. A green suite is silent on deployability —
  only the size gate speaks to it.

## 6. Compiler research snapshot (2026-08-08)

Pinned: solc 0.8.28. Latest stable: **0.8.36** (2026-07-09). Empirical probe on this codebase
(production profile, isolated out/cache): **byte-identical module size (21,198) and
equivalent compile time (~30s full tree)** — no size or speed win from upgrading today.
Reasons to schedule an upgrade anyway (calm moment, own PR):

- 0.8.34 fixed a HIGH-severity via-ir bug (transient/persistent storage clearing collision)
  affecting 0.8.28–0.8.33. This repo uses **no transient storage** (verified by grep), so it
  is not exposed — but staying under a version with a known high-severity codegen bug class
  is poor hygiene for a funds-adjacent surface.
- 0.8.32 fixed array clearing/copying that straddles end-of-storage (edge case; 0.8.28
  affected).
- 0.8.36 fixed an inheritance-order annotation bug affecting storage-layout analysis —
  relevant in principle to a deep linear chain like this one; our compiler-generated
  baselines pin the layout either way.
- The experimental SSA/stack-to-memory backend (0.8.35+, `--experimental`) and solx (LLVM,
  beta, "non-critical use") are not production-appropriate for this surface yet; re-evaluate
  in Q4 2026.
