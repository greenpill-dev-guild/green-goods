## B. Findings

### CP-AUD-001 · P0 BLOCKER · Contract Ready predicate crosses the contract/app boundary

**Lanes:** `contracts`, `state_api`, `ui_admin`, `qa_pass_1`, `qa_pass_2`

The contract authority makes the split explicit:

> `contract-spec.md:101` — “`markPoolReady(poolId)`, requires non-empty charter CID and a non-zero register provider-exposure cap. … **App additionally requires** one current non-revoked Baseline assessment … before offering the action.”

> `contract-spec.md:731` — “NotReady only; charter CID non-empty; non-zero provider exposure cap already set … **The app additionally requires** one current non-revoked Baseline assessment … before enabling this write.”

The dispatch handoff collapses those into one contract acceptance rule:

> `handoffs/codex-contracts.md:35` — “A pool cannot become Ready until its charter, at least one qualifying baseline, and a non-zero register exposure cap are present.”

The contract test plan and flow diagram reinforce the wrong layer:

> `contract-spec.md:792` — the `CommitmentPooling.t.sol` target covers “baseline/exposure-cap readiness.”

> `diagrams.md:293` — `NotReady --> Ready : markPoolReady (charter CID + current baseline assessment)`.

The diagram also omits the exposure cap, so it is wrong in both directions. A contracts agent can reasonably add an EAS/baseline check onchain or write a failing contract test for an app-only condition.

**Resolution direction:** `contract-spec.md` §5.1/§6.1 is the contract-layer authority. Keep `markPoolReady` gated on charter + non-zero register cap only; move the baseline assertion explicitly into shared/admin preflight and UI acceptance. Correct the contracts handoff, its test wording, D4, and any acceptance row that presents all three as onchain. If the owner actually wants an onchain baseline predicate, amend the interface, storage/dependency model, events, and EAS access design first.

**Confidence:** high. The same source states the layer split twice and the handoff removes it.

### CP-AUD-002 · P0 BLOCKER · Allocation is supplied at seed, but every admin derivative edits it at open

**Lanes:** `contracts`, `indexer`, `state_api`, `ui_admin`, `docs`, QA

The contract source of truth locks the allocation in `seedCycle`:

> `contract-spec.md:115-116` — “`seedCycle(..., allocation)`” and “`openCycle(cycleId)` … `CycleOpened` carries the six allocation-class bps (sum == 10000 validated at seed).”

> `contract-spec.md:551-559` — `seedCycle(... AllocationBps calldata allocation)`; `openCycle(uint256 cycleId)` has no allocation argument.

The UI contract instead makes allocation an editable step inside open:

> `uiux-spec.md:327-337` — “Hypercert allocation policy **at cycle open** … A step inside the open-cycle flow … every field stays editable … snapshot onto the cycle (emitted at cycle open).”

> `wireframes.md:409-423` — “Open cycle: allocation policy,” six editable percent fields, then `[ Open cycle ]`.

> `prototypes.md:368-369` — seed validates bps, then W11 edits allocation and calls `openCycle`.

> `hifi/screens/admin.ts:305-317` — “Open cycle — allocation policy,” editable bps rows, and `Open cycle` emits the snapshot.

The hi-fi also regresses the display-unit decision: `uiux-spec.md:337` and `wireframes.md:417-426` require percent fields, while `hifi/screens/admin.ts:296-310` renders raw bps.

**Why this blocks:** there is no ABI with which the drawn open-cycle editor can persist its edits. An admin agent would confidently ship a control whose submitted data has nowhere to go.

**Resolution direction:** `contract-spec.md` is authoritative. Put the editable allocation builder in the cycle seeding flow; render it read-only at open and continue emitting its stored snapshot in `CycleOpened`. Update §6.10, W11/SB-9, the hi-fi, and admin acceptance. If allocation must remain editable at open, change the contract API/state/event plan before any lane dispatch.

**Confidence:** high.
