## Style contract

Reference implementation: `artifacts/visuals/external-brief-loop.svg`. Paper `#FBF8F2`, ink `#2A2722`, stone text `#6E6857`, Built = fill `#DFEBDE` / stroke `#4C7A57` solid, Planned/gated = white fill / stroke `#988D77` dashed `5 4`, negation `#A65D57`, arrows `#988D77`, system font stack, rx 12, footer caption `Green Goods · Commitment Pooling — v1 (2026-08)`. Solid = Built/live, dashed = Planned/gated, everywhere.

Three clarifications added 2026-08-02, each after finding the same drift in more than one asset:

- **Card and panel outlines are stone `#988D77`, never ink `#2A2722`.** Ink is for type only. Four assets had drifted to ink outlines (`synthesis-ge-protocol`, `synthesis-three-layers`, `rollout-timeline-band`, `external-brief-money-map`); all are corrected. The tell is a card that reads hard-edged next to its siblings.
- **Ochre `#8A6D3B` is a named role: gated or later-roadmap.** It is a *sub-category* of dashed-Planned, not a competing convention — use it for something inside the wave but behind its own extra gates (borrow-and-repay) or for a roadmap seam that extends the shipped system (`synthesis-ge-protocol`'s partial functions). Plain dashed stone `#988D77` remains the default for ordinary Planned. Do not introduce a third accent; `#B98A3E` was one and has been normalized away.
- **The footer stamp is `v1` — no minor version.** `v1` names the Commitment Pooling release, not the asset's revision count, so `v1.1`/`v1.2`/`v1.4` were misreadings and are normalized. The date tracks **when the asset's claims were last reviewed**, not when the PNG was last rendered, so a pure re-render does not move it. A green check or red failure label may describe an authenticated lifecycle outcome inside a planned dashed boundary; outcome color never reclassifies the component as built. On paper, stone text passes 4.5:1 and planned boundaries/arrows pass 3:1; planned number badges use ink rather than white.

**Typography and accessibility contract**: optimize each source for a 624–720 px document placement, not only its 2× export dimensions. Body copy should normally use at least 16–20 viewBox units, with larger type where the canvas is 1000 or 1100 units wide; short evidence-state labels may use 14–16 only when the surrounding card and explicit solid/dashed treatment carry the same meaning. Every informative SVG requires `role="img"`, a unique `aria-labelledby`, and matching `<title>` + `<desc>`. The gallery's inline desktop view fits the complete composition to the reading column; the dedicated preview plane is the detailed-reading path, cloning the inline SVG or rendered Mermaid with zoom plus pan/scroll and focus return on close. **Rendered architecture diagrams fit to width, not to viewport height** (changed 2026-07-27): binding that inline view to a laptop-height plane drove the large ERDs to ~0.15 scale — roughly two-pixel type — so a tall diagram is now simply tall (against an absolute 1500 px ceiling) and the page scrolls past it. This applies to the Mermaid overview sizing only: the hand-drawn story SVGs keep their deliberate `height:min(78dvh,820px)` document-scale cap on desktop, and the preview dialog's **Fit** control still fits both axes by definition. Narrow screens fit the whole composition to the card rather than holding a 720 px floor, which used to show only the left quarter of an asset — usually empty canvas — and forced a pan before anything was visible.

**Content constraints (all assets)**: architecture diagrams and reusable synthesis diagrams stay garden-agnostic so they survive cohort changes. A narrowly labelled **case-study/story asset** may name Tech and Sun or another currently named garden only when it is used in that garden's external-document example, marks quantities and future behavior as illustrative/gated, and is not reused as general architecture. Presentation prose names the three confirmed candidate gardens only — the fourth slot is open and is never given a name (Decision Log #29). External-facing assets use the human role names Gardener, Garden Steward, Evaluator, Funder, and Community; implementation specs may retain `operator` as the permission term. A Need is a problem paired with a desired outcome; Request / Offer appears only as commitment direction. Show only the modeled ProtocolToGarden funding route (HoA → protocol Safe stays upstream). Whenever an asset quantifies the upstream pilot, use **$800 per month paid in G$, July through September 2026, $2,400 total**; never use a transaction-level G$ token count as the funding amount. Keep *Queued*, *Dispatched*, derived *delivery delayed*, derived *Celo executed / acknowledgment pending*, authenticated *Confirmed*, authenticated *Failed*, and origin-specific *Cancelled* distinct; cancellation is available before dispatch or after authenticated failure, never from delay. Show command retry and acknowledgment retry as separate paths and state that neither can execute G$ twice. The selected circulation return leg is gardens spending earned G$ on Green Goods team services; GoodDollar confirmed the arrangement and said they want to see circulation on 2026-08-08. Local merchant/store routes remain explicitly unmodeled, and partner claims still require evidence that circulation happened. No banned vocabulary (streak/countdown/leaderboard/FOMO/urgency terms); no rankings imagery.

**Canvas convention**: square (or ≤1.3:1) viewBoxes only — macOS `qlmanage` (the local render pipeline) slice-crops wide-landscape SVGs from the left, so wide canvases fail local verification even though browsers/Linear render them correctly. Square canvases are safe everywhere.

## Vocabulary source

Every state and enum label in these assets resolves to the machine-readable ontology sidecar, **`packages/shared/src/ontology/green-goods-ontology.json`** (human-readable render: `docs/docs/reference/ontology.generated.mdx`), which became repo canon with the ontology foundation on 2026-07-26. The commitment-pooling vocabularies carry `status: "spec"` and are transcribed from the contract and settlement specs, including contributor policy and payout-plan status.

Three rules bind the assets:

1. **1:1 mapping.** Display copy may prettify — a GraphQL mirror may read `APPROVAL_GATED`, an edge label may read "accepted (creator)" — but every label must map onto exactly one canonical member. No asset may introduce a term the sidecar does not carry; see `plan.todo.md` § *Ontology sidecar gaps* for the families flagged rather than invented.
2. **Provenance is visible.** The sidecar flags each state `on-chain`, `derived`, or `off-chain`, and the Architecture tab renders that: paper = on-chain, amber = derived, grey = app-only. **After editing any asset, rebuild the gallery** so the shared link reflects it. There are **two steps, and the second is not optional for publishing**:

```bash
bun .plans/active/commitment-pooling/visual-assets-prerender.ts
```

That script runs the builder read-only and then freezes the result, producing all three outputs:

1. `visual-assets-artifact.build.ts` writes the two build targets — three audience tabs: story (narrative opener + **21 Story sections**, including the three 2026-08-04 compatibility assets); **31 Architecture sections** (the hand-written opener plus 30 named D-sections) rendered as **43 Architecture Mermaid blocks**, which is also the gallery total since the Screens tab retired (D25 splits creation/lifecycle from settlement/offline recovery; D13 sits with the promise lifecycle; D27 covers Offer-over-time capacity; D28–D29 close future adaptability; every diagram carries an auto-derived colour key, every ERD a cardinality key, and every mixed-arrow diagram an arrow-meaning key); and Reference with the 37-asset coverage matrix, the un-numbered permission table, and the audited Open-questions findings panel, which now closes the tab. Screens live in the Flow Prototypes artifact only; the gallery links it from the masthead and Go deeper, and a build assertion keeps both links present.
   - `LOCAL_OUT` → `/tmp/cp-visual-local.DO-NOT-PUBLISH.html` — the complete local `file://` preview with the locked Mermaid runtime embedded. **This is the file to open for visual validation.**
   - `ARTIFACT_OUT` → `/tmp/cp-visual-artifact-body.DO-NOT-PUBLISH.html` — body content that still contains `<pre class="mermaid">`.
2. The prerender step renders every block through the already-installed Playwright chromium (light + dark), splices the resulting inline `<svg>` into the body, and writes `SHAREABLE_OUT` → `/tmp/cp-visual-shareable.PUBLISH-THIS.html`.

**Publish `SHAREABLE_OUT`, not `ARTIFACT_OUT`.** An artifact containing `<pre class="mermaid">` cannot be shared publicly — the host renders Mermaid at view time and unauthenticated viewers can't invoke that renderer, so the share is refused with "This version can't be shared publicly" (confirmed empirically 2026-07-22). The frozen body has no `<pre class="mermaid">`, no embedded runtime, and no external script references; the prerender asserts all three before writing.

### The one thing that keeps going wrong

Publishing the wrong file is the **only recurring defect in this pipeline** — 2026-07-22, 2026-07-31, and again 2026-08-01. It is worth knowing by shape, because it does not present as a publishing mistake:

> **Symptom**: the reader is told the latest version can't be viewed, or the share/version picker refuses. **`diagrams.md` is completely healthy.** It reads like a Mermaid rendering regression, so the hunt starts in the source and finds nothing.

**Diagnose from the published side first.** Fetch the artifact URL (WebFetch saves the full HTML locally) and grep that file — `<pre class="mermaid">` present and `dia-frozen` absent means the wrong build is live and the fix is a republish, not a source edit. A healthy published body greps as `<pre class="mermaid">`=0, `dia-frozen`=344, `<svg>`=158 (measured 2026-08-11 on the three-tab, 42-diagram build; re-measure after any block-count change).

Three guards now sit in the way, because bold prose here and a console warning in the builder both failed to stop it:

1. **The filenames say so.** The two unpublishable outputs carry `DO-NOT-PUBLISH`; the publishable one carries `PUBLISH-THIS`. The path string is the last thing read before it becomes the Artifact tool's `file_path`.
2. **A sentinel comment inside each body**, which survives renames and `*_OUT` env overrides. The builder stamps `GG-GALLERY-BUILD unfrozen`; the prerender swaps it for `GG-GALLERY-BUILD shareable` at the moment the body actually becomes publishable. If the two constants ever drift, the prerender hard-fails instead of quietly disarming the guard.
3. **A one-command verdict**, which the prerender also runs against its own output on disk, so the check that clears a file is the check that produced it:

```bash
bun .plans/active/commitment-pooling/visual-assets-prerender.ts --verify /tmp/cp-visual-shareable.PUBLISH-THIS.html
```

It prints `✅ SAFE TO PUBLISH` or `⛔ DO NOT PUBLISH` with the specific reasons, and exits non-zero on the latter. **Run it on the exact path you are about to publish.**

The builder hard-fails on missing or duplicate required D sections, Mermaid-count drift, a diagram-bearing section losing its diagram, a reading-guide section losing its panel, and any nav link that does not resolve to a section or sub-block anchor. The prerender additionally fails if any diagram does not render to SVG — its `render status: … (rendered N, failed 0)` line is the parse proof. `LOCAL_OUT`, `ARTIFACT_OUT`, and `SHAREABLE_OUT` may all be overridden by environment variable. W6 and the dissolved lo-fi variants are not standalone frames. Republish only after validating the local preview.

The per-asset SVG/PNG steps:

1. Edit the SVG directly (they are plain hand-written XML).
2. Validate: `python3 -c "import xml.etree.ElementTree as ET; ET.parse('<file>.svg')"`.
   **Never land an SVG edit without step 3 in the same commit.** The PNG is what gets uploaded to
   Linear and the Google Doc; the SVG is read by the gallery build but by no human reader. An
   SVG-only commit therefore publishes nothing while looking done, and the drift is invisible in
   review because the diff shows the corrected text. This has bitten once already — see § Asset
   status, 2026-08-01/02. Audit with:
   `for f in *.svg; do [ "$f" -nt "${f%.svg}.png" ] && echo "STALE: ${f%.svg}"; done`
   (identical mtimes are in-sync; confirm a hit with `git log -1 -- <file>.svg` versus `.png`).
3. PNG at 2x: `qlmanage -t -s <2xW> <file>.svg -o <dir>`, then rename `<file>.svg.png` → `<file>.png`. With square canvases this yields the exact 2x size with no cropping. (Headless Brave hangs on this machine with both `--headless` flags; qlmanage slice-crops wide-landscape SVGs — hence the square-canvas convention above.) **Non-square exception** (`artifacts/visuals/external-brief-loop.svg`, 1.3:1): qlmanage slice-crops even at 1.3:1 — wrap the SVG content in a temporary square 1800×1800 canvas (`<g transform="translate(0,105)">` for the 690-tall viewBox), render the square, then `sips -c 1380 1800` center-crops back to the exact 1800×1380 export (verified 2026-07-18).
4. Check dimensions: `sips -g pixelWidth -g pixelHeight <file>.png`.
