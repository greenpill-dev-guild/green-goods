The meeting's verdict — context-poor, not human-friendly, no flow, no links — is accurate, and the inventory explains why. The builder pages were authored in the repository's agent-contract register: the same compressed, authority-pointing prose as AGENTS.md, projected onto a public docs site. "This page is the shortest safe path for a code change." "Select honest validation." "Do not infer live health from an address." That language is excellent at preventing agent drift and terrible at welcoming a person.

The scale of it: all 28 hand-written builder pages together hold under 6,000 words — barely more than three community-track pages (Welcome + How It Works + one gardener guide ≈ 3,800 words). "How To Contribute" is 179 words, never mentions the Dev Guild, and defers to CONTRIBUTING.md — which defers straight back to the docs page. Neither contains the process. And at research time, not one page in the track linked to anything off-repo: not the EAS or Hats docs we integrate, not Playwright, not even our own live Storybook at design.greengoods.app. (The QA rewrite that landed this week added the first three, including qa.greengoods.app.)

The good news Two major assets survive intact. First, the target voice already exists in-house: the community track (1,100–1,500-word pages, benefit-led prose, outbound links, human tone) is the register to adapt, not a new one to invent. Second, the trust machinery is genuinely ahead of every reference site we studied — digest-gated generated pages, source_of_truth frontmatter, a docs audit in CI. Hats ships stale testnet lists; EAS ships pasted READMEs with LLM-editing residue; Octant runs two doc generations at once. Our pipeline prevents all three failure classes. The rewrite changes the prose and the shape, and keeps the machinery.
Moved since the research snapshot The feature/qa-report work rewrote both QA pages mid-discussion: Product Experience QA grew 630 → 1,514 words with real session steps (before / during / after the call, results by priority, slices), Test Cases grew to 4,123 words with priority bands and a case lifecycle, both now link the QA app, and GitHub Actions moved under deployments/. This proposal builds on that work rather than redoing it — the QA rows in Part 6 are now mostly keep.

Part 4

Convergent principles

Where three or more sources agree, treat it as settled. These become the working rules of the rewrite.

  1. Hubs navigate, leaves teach. A category landing is a curated set of links with one-line value props; context lives in the leaf pages. Never both jobs on one page.
  2. Every page ends with next steps. Two to four curated forward links. A page with no exit is a dead end — the direct cure for "no flow."
  3. Facts live in exactly one place. Addresses, schema UIDs, commands: one canonical page (ours is the generated deployment status), stubbed to from everywhere. Docs frame and link AGENTS.md and upstream docs; they never restate them.
  4. Outcome-first getting started, one safe path. Say what the reader will have at the end, walk one path that cannot surprise them, checkpoint with expected output, then offer named alternatives.
  5. Definition-first concept pages. The first sentence must survive being quoted alone.
  6. Link density is context repair. Octant's landing runs one link per 40 words. Every noun with a deeper page links there; every tool links to its own docs.
  7. Reader modes shape pages, topics shape navigation. Diátaxis's four modes (learn / do / look up / understand) govern how a page is written — but a monorepo's nav is organized by topic, and mixed-mode package pages are correct at our scale.
  8. One diagram per concept, simple. Hats explains trees with no picture; we explain 21 entities with one unzoomable picture. Both wrong — each concept gets one small, legible diagram.
  9. Machine-readable docs are a feature. Both GitBook sites ship llms.txt + .md twins; EAS's client-side rendering and Octant's bot wall nearly defeated this research. For a repo whose contributors are largely agent-assisted, this is cheap and on-brand.
  10. Migrate iteratively. Diátaxis is explicit: never stand up an empty skeleton, never big-bang restructure. Every improved page is worth publishing on its own.

Part 5b

Better than "Core Flows": Anatomy of a Work Submission

The journey pages are deleted (D2), and "Core Flows" died with them — rightly, because it was still five abstract flows wearing one page. The replacement is one concrete story: follow a single real work submission through every layer of the system, the way EAS teaches attestations by dissecting a live record and Octant teaches its mechanism with one worked example.

The page walks eight stages, each with two or three human sentences, a code pointer, and a link to the real thing:

  1. Capture — a gardener records work in the PWA, offline (media → details → review; the shared job queue holds it).
  2. Sync — connectivity returns; the queue replays through the authoritative path.
  3. Attest — the Work attestation lands on EAS via our resolver: the actual schema, the actual UID, linked live on arbitrum.easscan.org.
  4. Index — the Envio handler picks up the event and projects the read model (the GraphQL shape, linked).
  5. Review — the steward sees it in the admin cockpit.
  6. Approve — a separate WorkApproval attestation records the decision (also linked live).
  7. Display — status flows back to the gardener; the existing generated work-display-status sequence diagram slots in here, the one place it earns its keep.
  8. Onward — assessment, hypercerts, funding: one line each, linking the integration pages and the community guides.

Why this beats flow pages: it's the one page that makes the whole architecture felt — every package appears in its real role, every integration in context, and a reader finishes knowing where their future change would live. It pairs with the community "How It Works" as the technical rung of the explanation ladder (cross-linked both ways, the Octant pattern). The four commitment-* state diagrams from Sequences & States aren't part of this story — they move to the commitments layer of Data Model & Ontology, and the Sequences & States page dissolves.

Part 7

Page templates

Five skeletons, synthesized from the frameworks research and the best concrete pages found on the reference sites. Mixed-mode pages are deliberate — splitting a 400-word integration page into "explanation" and "reference" pages would recreate the fragmentation we're fixing.

Getting Started — the tutorial
  1. What you'll have at the end — one paragraph + screenshot of the running client. Outcome first, so readers self-select (Octant, Astro).
  2. Prerequisites — Bun/Node/Git/Docker as a checklist. Front-loaded self-assessment.
  3. Choose your path — Path A: full stack (bun run dev); Path B: single surface against hosted services. Octant's two named paths; the fastest route to a working screen wins.
  4. Steps 1–N — one command per step with expected output; environment setup lives here (absorbed from Environment Management), using ?mockAuth to avoid wallet friction. A tutorial "eliminates the unexpected" (Diátaxis).
  5. Checkpoint — "You should now see…" with screenshot.
  6. If something went wrong — the 3–5 real failures (dev:doctor, ports, Docker); everything else links out.
  7. Next steps — exactly three: System Overview · First Contribution · Testing Guide.
Package page — mixed-mode topic page
  1. What this package is — one sentence of purpose + where it runs in production (with live URL).
  2. Map — 5–8-row table of key directories/entrypoints. A map, not a census; the generated API Index is the census.
  3. Run and test just this package — the scoped commands.
  4. How it connects — upstream/downstream data flow, linking the Architecture pages. This is the "use cases and implementation context" the meeting asked for.
  5. Conventions that will bite you — 3–5 project-specific gotchas, one line each. Highest value-per-word content; unique to us.
  6. Go deeper — links: package AGENTS.md / README, live Storybook, generated references.
Integration page — hand-written meaning + generated detail (D4)
  1. Why Green Goods uses it — the meaning, purpose, and reason for the integration in one paragraph, definition-first. Hand-written; the grounding Afo asked for.
  2. How it flows through the stack — one small diagram: who signs, what's recorded, who reads it back.
  3. Where it lives in the code — linked table of the files/packages that touch it.
  4. Deployment projection — the current generated table (networks, recorded components), kept verbatim with its digest gate. Conditional: indexer section only when the integration is actually indexed.
  5. Working with it locally — how to exercise it in dev/tests without mainnet.
  6. Canonical upstream docs — 3–5 external links with one line each. For EAS: the SDK page, schema concepts, per-chain contracts page, arbitrum.easscan.org. For Hats: developer concepts hub, the viem SDK getting-started, the subgraph docs (the canonical answer to wearer enumeration), supported-chains page, app.hatsprotocol.xyz. Never paraphrase upstream at length (Octant, Hats).
Testing Guide — task page with a reference table (D1)
  1. Test map — one table: runner (Vitest / Playwright / Storybook / Foundry) × what it covers × where it lives × docs link.
  2. The everyday loop — targeted proof first, then bun run test:fast; when to escalate. Recommended path first; alternatives labeled.
  3. Per-surface commands — client / admin / shared / contracts / indexer subsections, commands only.
  4. Manual QA — ?mockAuth recipes, Storybook viewport checks, links to the live Storybook and the QA guide.
  5. Reproducing CI locally — what CI Gate runs and the local equivalent of each check.
  6. Writing new tests — where each test type goes + one linked exemplar file per type. Show, don't legislate.
Skills catalog — generated from per-skill READMEs (D8)
  1. Intro — two hand-written sentences: what a skill is here, how you invoke one. Hybrid, like integrations: meaning by hand, inventory by machine.
  2. Per skill (generated) — name · one-line purpose · when it fires · what it produces · link to the skill's folder on GitHub. Source: .claude/skills/<name>/README.md, the new convention; digest-gated like every generated page.
  3. Fallback rule — until a skill has a README, the generator projects its SKILL.md description so the catalog is complete on day one and improves as READMEs land. 13 skills today; READMEs are authored in the phase plan, and the same READMEs serve anyone browsing the repo (Codex included, via the .agents/skills symlink).
Part 8

Tone contract

Five mechanical rules (from Google's style highlights + the reference sites), applied to real sentences from our current pages. The register splits deliberately: hand-written pages sound like the community track adapted for developers; generated reference pages stay terse — every reference site we studied does exactly this split.

1 · Second person, active voice

Now"Shared exposes supported entrypoints through packages/shared/package.json. Client, admin, and agent consume those exports…"
Rewrite"Import from shared's declared exports — @green-goods/shared/hooks/… — never from src/ paths. The client, admin, and agent apps all follow this rule."

2 · Say why before what

Now"This page is the shortest safe path for a code change."
Rewrite"Green Goods is built by the Greenpill Dev Guild, and contributions of any size are welcome. Here's how to land your first change — from finding an issue to a merged PR."

3 · Goal or condition before instruction

Now"Run npm run setup only if Bun is not installed yet."
Rewrite"Don't have Bun yet? npm run setup installs it. Already have it? Skip straight to bun install."

4 · Plain declaratives; one idea per sentence

Now"Integrations cross different authority boundaries. Before changing one, identify which layer owns the fact you need."
Rewrite"Each integration touches several layers — contracts, indexer, app code. This table shows which layer owns which fact, so you change the right one."

5 · Links say where they go, and every page has them

Now"Storybook is the isolated contract for shared UI foundations." (no link — anywhere)
Rewrite"We develop shared UI in Storybook — browse the live instance at design.greengoods.app to see every component and its states."
