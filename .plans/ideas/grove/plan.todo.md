# Grove: implementation sequence

**Status:** idea-stage product. Nothing below is built except the disposable G0 spike, and no step is complete. **Created:** 2026-10-11. **Updated:** 2026-11-14.
**MVP contract and decision log:** [spec.md](spec.md).
**Acceptance gates:** [eval.md](eval.md).

Each unchecked step is a future, independently verifiable checkpoint. Checkpoint IDs are stable: a step that moved keeps its ID, and the 18 earlier S/P/K IDs are preserved below. Proposed paths are not existing APIs. Split checkpoints into bounded changes after inspection; do not duplicate storage or capture work.

## MVP order

The order follows two rules. The first is the owner's: "Local identity and key custody come first." The second is that the cheapest experiment able to change the design runs before anything is built on it.

| Order | Step | What it proves | Gates |
|---|---|---|---|
| 1 | C0b | Keys and captures survive on a real phone and a real laptop | E26 |
| 2 | C0a | The existing passkey can unlock a vault, and what happens where it cannot | E24 |
| 3 | C1 | The vault and the shared-file format reject what they must | E16 |
| 4 | C0 | Pairing, the member list, removal and the seven-day limit | E15, and E23 for its local cases |
| 5 | C0 and C1 together | Recovery of a lost device and loss of the steward | E15, E16, E24 |
| 6 | C2 | The whole loop by encrypted file on both clients, ending in a partner summary | E17, E2 |
| 7 | C4 | The supported device list, and what suspension and large files do | E19 for the file carrier |
| Alongside | S1 to S6, S8, S13 to S15, P0 to P2 | The laptop workspace: the agent's passive capture and assessment, the graph, and Pi, over Grove's own records | E1 to E4, E6, E12 to E14, E27, E28 |

The workspace lane can be built in parallel on synthetic records. It counts toward the [MVP finish line](spec.md#mvp-contract) only after steps 1 to 6 pass, and no private record enters it before then (D25).

**Next lanes, in the order they are likely to be needed:** a hosted mailbox with Solid as the preferred adapter (C1a, C3); the Admin Hub snapshot and digest (S7, S9); KOI exchange (K1, K2); co-editing (C5); outside accounts and publication (C6); the wider MVP of Milestone B (S10 to S12).

**Research, outside Grove's gates:** EDV, Automerge + Keyhive (E25), MLS, WebRTC transfer, Bluetooth sensors.

## Community-sharing delivery order

[The contract](community-sharing.md) owns the design; [the research](sharing-research.md) records what is unproven. This plan authorizes no implementation, dependency installation, tracker change or deployment. The entries are listed in the MVP order above, then the later lanes.

- [ ] **C0b — Key and capture durability on real devices.** New on 14 November (R5). On one physical phone and one physical laptop, with no protocol code: create a key pair and a few captures in the phone app installed to the Home Screen, in the same app in a browser tab, and in the packaged extension with a pinned ID (R12). Restart offline. Request persistent storage and record whether it is granted. Leave the phone app unopened for fourteen days, and read it once after eight: that is past Safari's seven-day limit and early enough to change the design. Clear site data. Reinstall the extension. Exit: E26. The result decides which phones may hold keys (R13). If an installed phone app cannot keep keys, the phone becomes a capture-only device that encrypts to the member's laptop key, and the plan changes before C0.
- [ ] **C0a — Passkey unlock, offline unlock and recovery on two devices.** A gate since 14 November (D19). Run [Pass A](collaboration-passkey-spike.md#pass-a-existing-passkey-offline-unlock-and-recovery) on real existing credentials from both populations: the `greengoods.app` credentials and the older per-site ones. Preserve the credential, its relying-party ID and the account recipe. Test the PRF secret on each passkey provider in use, the extension's route through host permission, a blocked network, a missing or refused prompt, a lost device, a lost credential, a corrupt export and a removed device whose passkey has synced back. Exit: E24. A provider that returns no secret gets the passphrase path; that passes the design and fails passkey unlock for that provider. No account migration, no new credential and no transaction.
- [ ] **C1 — Encrypted vault and shared files.** Choose between age v1 and HPKE on what the supported devices can run (R1, O3), and record the library, version, license and any audit. Define the signed manifest, the wraps of the vault key, how device private keys are wrapped under it when they are created and imported after unlock, and capture while locked (R15). Produce test vectors. Prove that a device that was not named cannot open a file; that a tampered, replayed or re-addressed file is rejected; that a copied browser profile without the unlock secret cannot open the vault; that no stored key can sign or decrypt while the vault is locked; and that no file name or content identifier of a private record reaches telemetry (R7). Exit: E16. No private pilot before this gate.
- [ ] **C0 — Identity, pairing, the member list and recovery.** Define the member list as one signed, hash-chained history with one active signer (R3, D18) and no identifier scheme beyond public keys (R2). Prove enrollment with no provider or wallet; pairing by scanned code and a spoken comparison string; a forged member or device entry; removal; the seven-day limit, a limit a community has changed, how an unchanged list stays fresh, and how a community whose devices are all stale shares again (D24); a second controller, its takeover when the first controller's devices and code are lost, and refusal of a fork (O6); the recovery code appointing a new controller device; and separate device keys per community (W3). Exit: E15 and the local cases of E23. Synthetic fixtures only.
- [ ] **C2 — Capture → review → share offline, on both clients.** Adapt the existing revision and command design for local workspace identifiers and encrypted payloads. Build explicit note, photo, file and link capture on both clients and page capture in the extension; manual personal review; the author's share approval, signed by the author's device and bound to a digest of the exact content (D17, R6); file export and import; the recipient's checks and signed receipt; review decisions and corrections; the author's fresh approval before a corrected version leaves; and a steward-approved partner summary as a new projection, carrying the steward's signed approval. Move captures from phone to laptop by file (D21). Use one knowledge source and one impact observation, and take each capture type through the loop once. No model, wallet, account or network. Exit: E17, E2 and the applicable parts of E1, E3 and E14, with no false Work, WorkApproval or publication state. Coordinate with S2 to S4, S6 and S8 instead of creating another store.
- [ ] **C4 — Phone boundary and device list.** Reduced on 14 November: WebRTC is research and no longer part of this step. Record the exact browsers and devices that pass, what phone suspension does to an export or import in progress, file size and retry limits, how the share sheet and file import behave on iOS and Android, and power use. Exit: E19 for the file carrier. No mesh or background-availability claim. Sensors remain import fixtures until separately scoped.
- [ ] **C1a — Hosted mailbox: the store interface, then Solid.** Next lane (D21). Define the store as opaque objects with put, get, list and delete by an unguessable name, and prove it first with any plain folder. Then follow [the two-device storage contract](storage-comparison-spike.md) on Solid with client-side encryption and local keys. Prove recovery, scoped access, host privacy with the operator's full view, migration and interruptions; record reused and new code, services, licenses and bundle cost. Exit: E22 and the applicable parts of E15 to E19. EDV stays an optional research variant. A failing privacy, permission or recovery gate blocks private use of that adapter; file exchange remains.
- [ ] **C3 — Solid adapter in the clients.** Next lane, after C1a. Pin provider, client and auth versions; prove sign-in and redirect in the extension and the phone app, CORS and CSP, token recovery and suspension. Store ciphertext, key wraps and manifests only; reconcile revisions and receipts; change provider without changing local identity; test the operator's full access with storage permissions bypassed. Exit: E18 and E22. A Pod sign-in never becomes identity or key authority.
- [ ] **C5 — Co-editing with Yjs; Automerge + Keyhive research.** Later lane, opened when two people must edit one draft at once (D16). Use the Yjs core for merging, one new document per audience, with every key holder able to write (R9). Prove encrypted updates, offline edits, restart and reconnect, removed and stale members, history and presence privacy, and recovery on a physical phone and laptop. Exit: E20; a server that can read the document fails it. [Pass B](collaboration-passkey-spike.md#pass-b-yjs-versus-automerge--keyhive) and E25 are backlog research and gate nothing (R11). MLS is a separate, conditional evaluation.
- [ ] **C6 — Outside accounts and publication.** Later lane. Prove private, separately approved associations with a garden or a service account. Verify EOAs and ERC-1271 accounts and the current garden role, and prove a garden link through a Hat-wearing account (R8). Record a release approval before anything is handed to an upload queue, bound to a digest of the exact payload (R6). Test Certified's EOA-only limit instead of claiming GardenAccount support. Scope ATProto/Certified, Ethereum and archival adapters one at a time with their owning projects. Exit: E21 and the outside-account cases of E23; no chain transaction or public upload is authorized by this plan.

**First complete demonstration:** a steward creates a community with no wallet → a member captures on a phone → reviews it by hand → pairs their laptop and carries the capture across as a file → shares a selected, encrypted copy with a reviewer → the reviewer corrects it → the author approves the corrected version → the steward sends a separately approved summary to a named partner. Then, on the laptop, the agent brings in a funding call that fits the community's focus while the member browses, and shows why it was brought in, where it came from and what to check before sharing; the member keeps it and shares it. A Gemma investigation proposes a connection, survives a closed tab, and the member accepts it in the graph. No Solid, EDV, co-editing, KOI, Hub, Certified or Ethereum dependency is needed. The phone needs no model.

## Before execution

The MVP order above governs. Do not put a live model, a Hub connection or a KOI peer ahead of local identity, encryption and manual capture and review.

Confirm the bounded build and its dependencies, select an isolated implementation checkout without changing another session's branch, and settle two open questions first: where the phone app and the shared core live (O2), and whether any Coop code may be copied (O5). This planning request is not an instruction to install dependencies or start product code.

The [prototype specification](prototype.md) proposed a thinner first build, G0 to G4, around a Hub connection, a Gemma investigation, a KOI exchange and agent tools. G0 ran as a disposable spike on 24 October. Of the rest, the investigation slice (G2) describes the workspace lane and still applies; G1's Hub connection, G3's exchange and G4's agent tools are next lanes (D22). Receipts a slice records still count toward the checkpoints it names.

This is Grove's canonical idea-stage hub. The [Grove project](https://linear.app/green-goods/project/grove-garden-knowledge-8582c2970974) is connected to Community Evidence Mesh; RESR-103 remains parent-only tracking, and its five project milestones still mirror the earlier A0 to A4 table below, not this order (O10). Once product execution is explicitly accepted, promote this hub and update its lane statuses. Run `node scripts/harness/plan-hub.mjs linear-sync --feature grove --json` and follow its actual create, update and preserve instructions under the repository's implementation start gate. Do not create a second active plan for the same feature.

Review the [Mesh mapping](mesh-alignment.md) before defining S2 contracts. Synthetic fixtures test mechanics without claiming Mesh evidence conformance. A real evidence pilot still requires the initiative's applicable metric, authority, consent and correction gates; personal graph review cannot satisfy them.

Before committing to the graph composition, use the [Claude Code design exploration](handoffs/claude-design-exploration.md). Its reviewable prototypes do not mark an implementation checkpoint complete. Compare the same fixture in both renderer candidates during S0, including label and edge readability as well as performance.

## Milestone A: the local garden loop

- [ ] **S0 — Prove runtime feasibility before feature build.** In a disposable approved extension fixture, evaluate one Gemma artifact in the packaged sandbox/offscreen arrangement and a Sigma graph in Brave. Record device, browser/runtime/model versions, cold/warm load, peak available memory evidence, completion, teardown and interrupted-job recovery. Test bundled code under the intended CSP. Use synthetic text. Exit: a reproducible local proposal with valid source IDs, or an explicit failed AI gate. Dependency/runtime choice is not finalized from source inspection alone.

- [ ] **P0 — Prove Pi browser execution and storage.** The spike on develop pins Pi Durable 1.5.0 and still runs it on in-memory storage, so the tab-close proof is owed; the release-age gate no longer blocks it. Record how a plain job row in Grove's own database handles the same investigation (R10). Follow [the execution contract](durable-execution.md). Split into (a) packaged portable-core/Chord bundle and single-owner host proof, (b) the upstream IndexedDbStorage from an approved compatible release plus storage/lifecycle checks, (c) reopen/termination and one prior-version migration fixture. Each is at most four files; a new Grove storage adapter is not planned unless the upstream implementation demonstrably fails the requirement. Use a pinned compatible approved version set; source commit and release are distinct. Exit: storage conformance and Brave stop/reopen pass without Node shims, cloud fallback or competing Harness writers; serialized Pi state has references only. A failure blocks Pi product integration.

- [ ] **S1 — Create the extension's minimal composition.** New `packages/extension/package.json`, `wxt.config.ts`, `entrypoints/background.ts`, `entrypoints/graph/index.html`. Register build/test/source-structure coverage through existing owning configurations as a separate bounded follow-up if necessary. Follow root env, i18n and package rules; no broad capture permissions. Exit: an unpacked Brave extension opens one graph page and reloads without losing installation identity. The tiny spike does not become an unreviewed production manifest.

- [ ] **S2 — Define the shared contracts and fixture.** In the MVP, S2 owns the contracts for Grove's own records only: captures, the community's focus, assessments and connections. The Garden snapshot belongs to S7 alone. Proposed Shared files: `modules/garden-knowledge/contracts.ts`, `modules/garden-knowledge/ontology.ts`, a focused contract test and declared export update. Define edge provenance, the personal review vocabulary and the composed profile/pinned pack format from [ontology alignment](ontology-alignment.md). Preserve upstream IDs and independent protocol, Commons editorial and local review states; replace the earlier Source/Claim placeholders with explicit draft mappings. Split profile/schema mapping into its own bounded checkpoint if the file budget requires it. Prepare synthetic fixtures for a knowledge capture, an impact observation, a focus and an assessment. Define activity class and optional planned time separately from review; pin domain/profile and wire versions independently. Exit: reject unknown predicate/type mappings and keep capture, focus, assessment and connection identities distinct. Do not hand-edit generated ontology output.

- [ ] **S3 — Build durable revision storage.** Proposed Extension files: `knowledge/schema.ts`, `knowledge/store.ts`, `knowledge/store.test.ts`. Add transactions for source/entity/assertion revisions, changes, dispatch intent and prepared commands. Reserve scoped inbox/outbox and peer-state transactions for K1. Pi owns investigation scheduling; deterministic intake/delivery workers retain only their own leases. Expected-revision checks own review conflicts. Exit: duplicate ingestion is a no-op, failed transactions are invisible, and acknowledged revisions survive reopening.

- [ ] **S4 — Add temporal projection and query.** Proposed files: `knowledge/query.ts`, `knowledge/query.test.ts`, `knowledge/view-state.ts`. Implement as-known-at-sequence, compare sequences, two-hop selection, source/review/type filters and explicit seen cursor. Exit: late imports, new edges between old nodes, corrections and workspace filtering pass the temporal cases in E2/E3.

- [ ] **P1 — Add idempotent graph commands and dispatch.** Proposed `knowledge/commands.ts`, `knowledge/commands.test.ts`, `execution/dispatch.ts` and its admission test, split again if store integration exceeds four files. Atomically write graph revisions with command receipts, and source/review changes with dispatch intent. Bind stable run/command keys to workspace and input/payload digests. Atomically pair the Pi run-index key with `tx.createTask` in one Pi commit; custom-task admission must not invoke built-in model generation. Exit: crash after graph commit but before Pi checkpoint returns the same receipt; a different payload under that ID, stale revision, or erased source rejects; interrupted admission creates one run. Prerequisite: S2–S4 and P0.

- [ ] **S5 — Build graph canvas and subscription.** Proposed files: `graph/GraphCanvas.tsx`, `graph/renderer.ts`, Shared `hooks/knowledge/useKnowledgeProjection.ts`, a consumer test. Use a supplied projection subscription rather than a Shared import of Extension internals. Deterministic initial placement and saved coordinates precede force layout. Exit: committed changes patch the graph without resetting camera/selection; opening another tab sees the committed sequence.

- [ ] **S6 — Add graph controls and review inspector.** Proposed files: `graph/GraphView.tsx`, `graph/GraphControls.tsx`, `graph/GraphInspector.tsx`, focused interaction test. Wire the path from an overview of the community's records to a topic to a source, with the Back control. In the MVP the overview shows Grove's own records; a garden's public records join it with S7. Also wire query/filter, timeline, evidence quote, independent planned/reported/recorded labels, review/correction and text results. Add required translations in a bounded accompanying checkpoint. Exit: keyboard user can inspect/review the same result as a pointer user; a stale review is rejected visibly.

- [ ] **S7 — Connect the Hub through a bounded snapshot.** Next lane (D22); choose the connection design first (O9). S7 alone owns `GardenSnapshotV1`, the Garden, Action, Work and WorkApproval mappers, their synthetic mapper cases, and the source-backed Vida Verde and TAS fixture manifests, all of which moved here from S2. Shared `modules/garden-knowledge/snapshot.ts` and its test own the mapping from existing readers; Shared `hooks/knowledge/useGardenKnowledgeBridge.ts` owns the React transport subscription. Extension `entrypoints/hub-bridge.content.ts` owns the restricted relay. Split Admin connect/open wiring into its own checkpoint in `views/Garden/components/` plus the existing garden composition. Exit: origin and garden-scope rejection tests pass; connected Hub transfers a bounded snapshot for each named garden, repeats safely, and reports partial coverage. Unavailable garden records remain an explicit integration blocker; do not fabricate them. S7 completes the real garden-data path, not merely a fixture import.

- [ ] **S8 — Capture, infer and review one source.** Split into two bounded checkpoints: (a) `runtime/capture.ts`, `knowledge/ingest.ts`, their behavior test; (b) `runtime/inference.ts`, offscreen entrypoint, packaged sandbox entrypoint and message-validation test. Adapt only the justified Coop code after source rights are resolved. The source commits before enrichment. Exit: the real local model produces bounded schema-valid candidates from the selected fixture packet; P2 owns Pi task integration and mutation recovery. Accept/correct creates history; reopening offline preserves it. A fixture inference stub cannot pass E4.

- [ ] **P2 — Run a durable local investigation and review continuation.** Proposed `execution/investigation.ts`, its interruption test, `execution/gemma-step.ts`, and a scoped progress projection; split UI wiring/erasure proof into a separate bounded checkpoint. Use custom phases and the existing Gemma bridge, not a built-in tool loop. Checkpoint references to prepared commands, apply through P1, and finish as ready for review. A human review dispatches a new keyed follow-up without a live wait. Exit: E13/E14 pass for source-save/admit, inference, prepared-result, graph-commit and Pi-checkpoint interruptions; one owner remains; erased source text never enters/restores through Pi records. Prerequisites: P0/P1, S6/S8.

- [ ] **S13 — The community's focus.** Added 14 November (D30). The steward writes the community's topics, goals and open questions as a community record with revisions. A steward's device signs each revision, and a client accepts a focus only when a device the current member list names as a steward signed it. After a change of steward, the new steward signs the focus again. Members receive it like any shared record, and each member's agent reads the copy on its own device. Exit: a focus written on one device reaches another by shared file; a change is a new revision; a focus signed by a member who is not a steward, or by a removed steward, is refused and shown; and with no focus the agent brings in nothing. Prerequisites: S3 for storage, C0 for the member list, C2 for sharing.

- [ ] **S14 — Passive capture as the person browses.** Added 14 November (D26 to D28). In the extension, read the text of pages the person visits, except private windows, the block list and pages with a password field (R18). Judge relevance in two stages: a plain text match against the focus, then one model step on pages that match, queued for when the laptop is idle (R16). Give the queue a limit on size and on age, set from E27's measurements, and drop page text past either. Bring in only what the model judges relevant, as a capture in the person's own inbox, and keep nothing from any other page (R17). Show when the agent is reading, give a pause switch, and list what it brought in. Deduplicate by address and content. While the vault is locked the agent reads nothing, drops queued page text and cancels a check in progress. Exit: E27. The request for access to all sites is a manifest change that needs its own review (O12).

- [ ] **S15 — Assessment before review.** Added 14 November (D29). For each item the agent brought in, run three bounded Pi phases: why it was brought in, with the passage; its source, author and date, with the deadline for a funding call; and what to check before sharing, such as names, contact details and exact locations. Store the result beside the item with the model version and what could not be checked (R19). Show it in review, where the person keeps, corrects or discards. Exit: E28, including one brought-in item kept, approved and shared through C2's file path. The assessment never shares, approves or discards.

- [ ] **S9 — Return reviewed insight to the Hub.** Next lane (D22). Shared digest contract/mapping, an Admin digest component and its consumer test, plus the existing bridge handler. Show only included accepted items, source references and graph links under the exact garden binding. Exit: an accepted item appears as **On this device**; rejected/raw/private items do not escape by default; disconnect stops exchange. No backend mutation is introduced.

**Local checkpoint:** connect → source capture → keyed Pi investigation → real proposal → idempotent graph command → graph review/follow-up → temporal comparison → offline resume → same-device Hub digest. P0–P2 are required for this selected architecture. This proves the local path, not the KOI spike. In the MVP the checkpoint runs from source capture to offline resume; connect and the Hub digest belong to the Hub lane.
