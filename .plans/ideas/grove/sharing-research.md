# Grove sharing research: standards, Coop and browser limits

**Inspected:** 13 November 2026. **Question:** how can Grove support community-controlled identity and encrypted capture → review → share on existing devices? This note supplies evidence for [the proposed contract](community-sharing.md); it does not certify implementations. **Established** means observed in a cited specification/source, **inferred** means an architecture conclusion, and **unresolved** means a required spike.

## Recommendation and alternatives

**Inferred:** retain Solid as the first optional hosted-storage adapter; keep Grove identity, encryption and export independent of it. Compare EDV envelopes and delegation before selecting a crypto library. Do not build two hosted sharing stacks. Keep offline bundles as the baseline when no provider is reachable.

| Candidate | Established capability and standards status | Implication for Grove |
|---|---|---|
| [Solid Protocol 0.11](https://solidproject.org/TR/protocol) | HTTP resources, WebID, authentication and WAC/ACP authorization. Published as a Solid Community Group report, not a W3C Recommendation. | Suitable optional Pod storage. ACLs are enforced by the server; content needs application E2EE to exclude that operator. |
| [W3C Linked Web Storage WG](https://www.w3.org/2024/09/linked-web-storage-wg-charter.html) | Standards-track work on separating apps, storage, identity and access control, growing from Solid incubation. The [W3C inventory](https://www.w3.org/TR/) lists a 9 November 2026 protocol draft. | Watch as the standards path related to Solid, not an independent drop-in product. Pin actual server/client versions; draft publication does not establish compatibility or E2EE. |
| [Encrypted Data Vaults v0.2](https://identity.foundation/edv-spec/) | Joint W3C CCG/DIF work on provider-blind encrypted storage, indexing and multiparty access. Work resumed in August 2026; the document calls v0.2 transitional. Several extensions remain unspecified. | Closest standards-community alternative for this confidentiality requirement. Evaluate an actual maintained browser implementation and key/revocation behavior; not a ratified W3C Recommendation or an automatic group-governance solution. |
| [DIF Decentralized Web Nodes](https://identity.foundation/decentralized-web-node/spec/) | Draft for DID-associated storage/message relay, roles, permissions and replicated nodes. | Strong conceptual fit for identity-led data exchange; current implementation maintenance, browser packaging, encryption defaults and interoperability need separate proof. Not selected for the first adapter. |
| [remoteStorage](https://remotestorage.io/protocol) | WebFinger discovery, OAuth-scoped HTTP storage and offline-capable sync. Protocol version 2 plans PKCE; earlier versions use implicit grant. | A narrower bring-your-own-storage alternative. Still needs Grove E2EE and community membership; assess current auth/library support before use. Its Internet-Draft is not proof of IETF ratification. |
| [Willow](https://willowprotocol.org/specs/index.html) | Independent protocol family with capabilities, confidential synchronization and transport-independent Drop Format. Not a W3C/IETF standard. | Worth a later offline/store-and-forward comparison. Browser maturity, bundle cost and integration are unresolved; do not add it alongside Yjs and Solid speculatively. |

The [W3C CCG Capability-Based Storage Task Force](https://github.com/w3c-ccg/capability-based-storage-tf) is a useful place to follow EDVs and delegation work. A Community Group work item has a different maturity/status from a W3C Recommendation. DID Core and Verifiable Credentials address identity/claims; they do not replace encrypted storage or transport.

## Encryption options and browser feasibility

- [Web Crypto](https://www.w3.org/TR/WebCryptoAPI/) provides crypto operations such as AES-GCM. It does not establish device trust, rotate a community's recipients or recover a lost vault. Select a reviewed library/format for envelope/key wrapping. [HPKE RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) is a CFRG/IRTF Informational RFC, not an IETF Standards Track RFC; it provides recipient encryption, not the rest of Grove's authorization system.
- [MLS RFC 9420](https://www.rfc-editor.org/info/rfc9420/) is IETF Standards Track group key establishment with forward secrecy and post-compromise security. [RFC 9750](https://www.rfc-editor.org/info/rfc9750/) explains the surrounding application architecture. Browser packaging, persistent epoch state, multi-device identity, offline changes and implementation security still need proof. Evaluate for collaborative groups rather than choosing it merely because a community has members.
- [WebAuthn PRF](https://www.w3.org/TR/webauthn-3/#prf-extension) can supply client-side key-derivation input where supported. It is distinct from treating an ordinary passkey assertion as a stable secret. Feature detection, RP/origin scope, user activation, replacement devices and recovery are unresolved for Grove's exact extension/PWA combination.
- [Inrupt's JavaScript SDK](https://docs.inrupt.com/sdk/javascript-sdk) supplies browser Solid clients and authentication. The [Community Solid Server](https://github.com/CommunitySolidServer/CommunitySolidServer) is a separate server runtime. **Inferred:** extension client integration is feasible, but running a conventional Pod entirely inside MV3 is not an established deployment. Test [extension auth callbacks](https://developer.chrome.com/docs/extensions/reference/api/identity), public-client redirects, CORS/CSP, token storage and [worker suspension](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).
- [Spaces alpha](https://atproto.com/blog/atproto-spaces-alpha) remains explicitly experimental; the [permissioned-data proposal](https://github.com/bluesky-social/proposals/blob/main/0016-permissioned-data/README.md) excludes E2EE from scope. Its [6 November sync update](https://atproto.com/blog/space-sync) describes the forthcoming Group Host. Spaces can control access without excluding operators from plaintext. It is optional and unnecessary alongside Solid for the first pilot.

## Carriers and a realistic community network

| Mechanism | What the primary source establishes | Grove implication / unresolved proof |
|---|---|---|
| [Yjs updates](https://docs.yjs.dev/api/document-updates) | Binary updates/state vectors can reconcile document state across transports. | Merge engine only. Encrypt before persistence/transport, verify authors and permissions, partition audiences, and keep governance outside mutable shared state. Immutable capture/review exchange does not initially require CRDTs. |
| [WebRTC peer connections](https://webrtc.org/getting-started/peer-connections) | Data channels connect peers; signaling is separate, and ICE/STUN/TURN handle connectivity. | Active devices can transfer ciphertext directly. Verify peer fingerprints/identity; DTLS is not the persistent content-encryption layer. Prove LAN-only signaling separately from internet signaling and restrictive-NAT TURN. |
| [Web Bluetooth](https://developer.chrome.com/docs/capabilities/bluetooth) | Supported browsers act as a BLE central connecting to remote GATT peripherals, with explicit device selection/user gesture. | Useful sensor adapter. It does not supply browser-to-browser peripheral advertising or automatic multi-hop phone mesh. No universal browser/device support claim. |
| HTTPS/WSS | Transport protection ends at the server. | Use HTTPS for Pods and encrypted record transfer; a relay must carry opaque content. Optional WSS is justified only for live collaboration/signaling. Ordinary server-side Yjs processing is a different trust boundary. |
| Encrypted file bundles | A Grove proposal using the same versioned envelopes over OS file sharing or removable storage. | First offline transfer fallback. Must test duplicate import, stale membership, interrupted transfer, blob limits and restoration; a QR pairing code is not a bulk media channel. |

**Inferred:** use a phone companion and desktop extension before promising a cross-platform phone extension. Keep the phone capable of local capture without the laptop/model. An app opened on each device may sync when active; suspended mobile browsers and closed extensions are not always-on relays. A community-run laptop service can improve availability, but remains optional infrastructure with an explicit maintenance cost. Full multi-hop forwarding is later research, not a WebRTC/Yjs feature implied by choosing those libraries.

## External identity connections

[DID Core privacy guidance](https://www.w3.org/TR/did/#privacy-considerations) supports minimizing correlation. [did:key](https://w3c-ccg.github.io/did-key-spec/) cannot update/deactivate; [peer DIDs](https://identity.foundation/peer-did-method-spec/) warrant method-specific recovery/rotation evaluation. [VC Data Model 2.0](https://www.w3.org/TR/vc-data-model-2.0/) is an optional signed-claims model, not an encryption or automatic selective-disclosure implementation.

[Certified PDS documentation](https://docs.hypercerts.org/reference/services/certified-pdss) allows other PDSs, including a community's chosen provider. [Certified Group Service](https://docs.hypercerts.org/reference/services/certified-group-service) holds group-account credentials and mediates role-based writes, while reads go through the PDS. **Inferred:** use it as a deliberate delegated publishing service; it need not control Grove membership or private keys. ATProto itself should not be described as necessarily centralized to Certified. Its [DID spec](https://atproto.com/specs/did) currently supports `did:plc` and `did:web`; an offline local DID needs an explicit account association rather than working as an ATProto account automatically.

Ethereum linking uses [CAIP-10](https://standards.chainagnostic.org/CAIPs/caip-10), [SIWE](https://eips.ethereum.org/EIPS/eip-4361) for sessions, or a scoped [EIP-712](https://eips.ethereum.org/EIPS/eip-712) statement, with nonces/expiry and audience checks supplied by the application. [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271) covers contract-account signature verification. The inspected [Certified EVM-link schema](https://github.com/hypercerts-org/hypercerts-lexicon/blob/main/lexicons/app/certified/link/evm.json) supports EOA EIP-712 proofs; contract-wallet compatibility is unresolved. A public binding exposes a correlation even if each identifier is pseudonymous.

## Existing Green Goods boundary

Source inspection in the current shared checkout, base HEAD `a0d503abc`, with unrelated local edits present: [GardenAccount](../../../packages/contracts/src/accounts/Garden.sol) inherits the tokenbound account and delegates roles through Hats; the [signature implementation](../../../packages/contracts/lib/tokenbound/src/abstract/Signatory.sol) implements ERC-1271. [Wallet work submission](../../../packages/shared/src/modules/work/wallet-submission/submit-work.ts) uploads media/metadata before submitting its public attestation. This is source evidence, not a deployed-chain audit.

**Inferred:** put Grove's public-release review before calling any existing upload/submission pipeline. Do not reuse the public Work queue for encrypted community records. A local workspace must exist without chain/address; add public garden bindings later. Protocol Work and WorkApproval keep their existing canonical IDs and authority. No runtime or contract change is made by this plan revision.

## Research stop and next proof

Proceed with C0–C5 in [the delivery plan](plan.todo.md#community-sharing-delivery-order): local identity/recovery; encrypted envelopes; offline flow; Solid integration; direct networking; optional collaborative draft comparison. The design is sufficiently bounded to prototype with synthetic data. Sensitive community content waits for identity, recovery, encrypted transport and recipient-isolation evidence. No claim of an audited cryptographic implementation, a working phone mesh or production E2EE is made here.
