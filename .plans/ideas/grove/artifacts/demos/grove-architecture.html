Grove, from local to shared

How one capture moves from a person's own device to their community, to a partner community, and later to the public. Each crossing is a separate decision with its own approver.

Proposed architecture. Nothing on this page is running software, and no property shown has been tested. It reflects the decisions recorded on 14 November 2026. Examples are synthetic; the page holds no keys or accounts and stores nothing.

Who holds which key

Identity, device authorization, content keys and service logins are separate. No provider account sits at the root.

Keys and secrets in the proposed design
Key or secretHeld byWhat it doesIf it is lost
Existing Green Goods passkeyThe person, through their passkey provider. It can syncUnlocks the vault where the provider supports it. It never identifies a device, signs a record or opens a shared fileUse the passphrase or the recovery code
PassphraseThe personUnlocks the vault wherever passkey unlock is unavailableUse the recovery code
Recovery codeThe person, off the device. For a community, the stewardOpens a recovery export. For a community, appoints a new controller device and nothing elseA second device or a second controller. Otherwise nothing can be recovered
Vault keyEach device, stored wrappedProtects private keys and records at restRestore from a recovery export
Device keysEach device, a separate pair for each community. Never exportedOne signs what the device sends. One opens files addressed to the deviceEnrol a new device. A lost device key is never revived
File keyNobody keeps it. It travels inside each shared file, wrapped once per recipient deviceEncrypts one shared fileRemoving a member needs no rotation: the next file is not wrapped to them
Controller keyThe steward's device. A second controller before real dataSigns every change to the member listThe recovery code appoints a new controller device

Whoever stores or relays a shared file sees its size, its timing, addresses and how many recipients it has, and never its content. Green Goods publishes the client code and is trusted: the phone app is served from the web, so its publisher could ship code that reads an unlocked vault. A device that is unlocked or compromised exposes what it can open, and removal cannot make a recipient forget what it already received.

What is in the MVP, and what comes after

MVP

  • A phone web app and a desktop extension, shipped together
  • Capture and manual review with no wallet, account, model or network
  • Passkey unlock where supported, passphrase otherwise, and a recovery code
  • One steward signs the member list
  • Sharing by encrypted file
  • On the laptop: an agent that brings in relevant pages as you browse and assesses each one, a graph of Grove's own records, and Pi investigations
  • The steward writes the community's focus, which tells the agent what is relevant

Next lanes

  • A hosted mailbox, with Solid as the preferred adapter
  • The Admin Hub snapshot and digest
  • KOI exchange
  • Co-editing with Yjs
  • Publication: Green Goods, ATProto or Certified, IPFS or Filecoin

Research

  • Encrypted Data Vaults
  • Automerge with Keyhive
  • MLS group keys
  • WebRTC transfer
  • Bluetooth sensors
