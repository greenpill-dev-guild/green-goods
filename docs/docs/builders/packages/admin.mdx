# Admin

`packages/admin` is the steward cockpit at [admin.greengoods.app](https://admin.greengoods.app):
where stewards review submitted work, manage gardens and actions, and run their community's
operations. It's an operator surface by design, so it favors utility copy, one dominant workspace
per route, and restrained color over marketing polish.

## The shell

The canonical shell is `CanvasLayout`: an admin-owned top `AppBar` (garden chip, search, account
actions), the `.workspace-canvas`, a `MainSheet`, and a bottom `NavigationBar` with exactly four
items: Hub, Garden, Community, Actions. Every workspace overlay is a centered `AdminDialog`;
profile, settings, and notifications render in a right-docked `AdminSideSheet` (bottom sheet on
mobile). The `/hub` route is the reference surface for new page composition.

## Run and test

```bash
cd packages/admin
bun run test
bun run build
```

`bun run test:coverage` is the fuller pass. Visible UI changes also want rendered proof; the
package guide describes the authenticated browser QA path.

## How it connects

The admin reads through the same [indexer](./indexer) read models and shared
[EAS data layer](../integrations/eas) as the client, and writes approvals through the
[contracts](./contracts). Its building blocks come from [shared](./shared); the admin package owns
the forked cockpit shell and the `Admin*` wrapper components.

## Conventions that will bite you

- Use the admin wrapper inventory (`components/Admin*.tsx`) and the surface classes
  (`.surface-section`, `.surface-card`, `.workspace-canvas`) before composing raw
  border-and-shadow layouts.
- `NavigationBar` is pure navigation. No leading or trailing slots, no extra items.
- The client PWA's `AppBar` pattern doesn't belong here; admin has its own.
- `DashboardLayout`, `Sidebar`, and `Header` are legacy migration code, not templates for new
  work.
- Cards mark discrete records or action targets, not decoration; avoid nested bordered-panel
  mosaics, hero sections, and promo banners.
