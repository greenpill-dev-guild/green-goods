# Product Experience QA

<StatusBadge status="In progress" />

Green Goods is not ready to call a frontend change complete merely because it builds, passes unit
tests, or reaches a contract successfully. Product experience QA must prove that a person can find,
understand, use, recover from, and complete the intended journey without layout, interaction,
language, accessibility, or state defects.

This standard covers four product surfaces:

- the steward-facing admin console;
- the installed client PWA;
- the public editorial website in the client package;
- the Docusaurus documentation site — a first-class surface with its own journey matrix below,
  because it is where builders and community members learn the product, and its glossary anchors
  are a client-facing API.

## Release decision

A user-facing change is ready only when both proof layers pass:

1. **Behavior proof** confirms that state and data change correctly, including loading, failure,
   recovery, permissions, and asynchronous completion.
2. **Experience proof** confirms that the real rendered journey is understandable, operable, and
   visually coherent at the required viewport, role, locale, and data state.

A green behavior test cannot overrule a visible product defect. A Storybook story cannot substitute
for an authenticated route when identity, permissions, wallet state, installed-app behavior, or live
data materially changes the experience.

## Evidence hierarchy

Use the strongest available evidence and say which layer was reached.

| Layer | What it proves | What it does not prove |
| --- | --- | --- |
| Source and mechanical checks | Types, tokens, vocabulary, route declarations, build integrity | The rendered journey is usable or polished |
| Component and Storybook proof | Isolated states, interaction contracts, component geometry | Route composition, real identity, live data, or recovery behavior |
| Clean-room built-route proof | Entry, routing, overflow, console health, selected responsive checks | Authenticated or profile-dependent behavior |
| Authenticated Brave proof | The actual local journey for the selected identity, role, locale, and data | Other roles, devices, states, or production deployment health |

For admin, PWA, wallet, installed-app, staging-session, and profile-dependent claims, authenticated
Brave is required. Clean-room browser checks remain useful secondary evidence and must be labeled as
such.

**Capability blocks name the harness.** Different agent harnesses reach different evidence layers:
a sandboxed agent without the authenticated-Brave extension path cannot produce layer-4 evidence
that Claude Code with the connected extension can, and some flows (real-device installs, passkey
ceremonies) are human-only. A finding that could not be verified because of the *verifier's*
environment is recorded as `Capability blocked (<harness>, <missing capability>)` — never stated
as a universal blocker, and never silently upgraded to a product defect. Conversely, a `Blocker`
label requires reproduction in a warm, authenticated environment.

## Required QA matrix

Every release or substantial UI pass should mark each applicable row `Pass`, `Fail`, `Blocked`, or
`Not applicable` (`N/A` in the workbook and Sheet — same value). `Blocked` is not a pass and must
name the missing capability or data.

The executable form of this matrix is the versioned test-case catalog:
`scripts/data/qa-test-catalog.json` (v2) holds the scenario definitions across four surfaces —
Public Website, PWA, Admin Dashboard, Docs. Test IDs are `PUB-`, `PWA-`, `ADM-`, and `DOCS-`;
installed-device rows keep their `PWA-IOS-`/`PWA-AND-`/`PWA-ROLE-` prefixes inside the merged
PWA surface, and two legacy `XPLAT-` rows survive from the dissolved Cross Surface tab (retired
rows keep their historical tabs as an audit trail). `bun run qa:workbook` projects the active
cases into a simple human-first run sheet: an Overview tab (run info filled once, how-to, live
per-surface counts) plus one tab per surface with plain-language columns — ID, priority, what we're checking,
how to check, what should happen, result, severity, notes — grouped by area. Defect records stay
in the private **Green Goods v1.1 QA** Sheet. Definitions are reviewed in git; results, owners,
and defect links live only in the run sheet, the Sheet, and Linear — never in this public repo.
The journey tables below are the narrative contract those cases decompose.

### State and quality dimensions

Apply these dimensions to every applicable journey, not just to primitives in isolation:

- default, hover, focus-visible, active, selected, and disabled;
- loading, skeleton, empty, partial data, error, retry, success, and stale data;
- authorized, unauthorized, own record, another person's record, and expired or completed record;
- short, long, missing, malformed, translated, and user-authored content;
- narrow mobile, common mobile, tablet or narrow desktop, and wide desktop as applicable;
- online, slow network, offline, reconnected, and duplicate-action protection;
- keyboard-only, visible focus, accessible name, focus return, dialog containment, and reduced motion;
- light and dark theme where the surface supports both;
- no clipping, overlap, accidental scroll traps, horizontal overflow, invisible text, or controls
  covered by fixed chrome.

## The QA session loop

The canonical polish process is the founder-led **QA session**, owned by the `qa-session` skill
(`.claude/skills/qa-session/SKILL.md`): the founder walks real flows on the local stack against
production data — their own Garden and the community Garden, switched via `?gardenId=` — while
dictating observations; the agent copilots. The loop:

1. **Pre-flight** — same-checkout guard (fixes must land in the checkout serving ports
   3001/3002), `bun run dev:prod`, warm-up loads before dictation, an identity plan, and a
   real-write boundary agreed once (dev:prod wallet transactions are real Arbitrum writes).
2. **Capture** — every dictated item is logged immediately with a stable `OBS-NN` id, the
   verbatim quote, surface + route, a quiet component resolution, and the catalog `case:` id
   when matched. The walk is never stalled by diagnosis.
3. **Live triage** — one-line fix-now vs defer proposal per observation. Fix-now requires small
   size (≤30 min, ≤3 files, binding timebox), presentation-level blast radius, HMR
   validatability, and reversibility; everything else defers.
4. **Fix and revalidate** — accepted fixes are edited live, the founder revalidates through HMR
   in their open tab within the same session, and each fix commits with its OBS id.
5. **Close** — deferred items hand off to `qa-triage` as a pre-structured session log; results
   rows go to the run workbook and Sheet; dictated `decision` items pass through a lock gate
   into the design decision ledger (`.claude/skills/design/decision-log.md`) so polish rulings
   compound into guidance; a session receipt (results, fixes, environment notes, remaining
   risk) is stored in the private Drive QA folder — never committed.

A recorded dictation transcript of a completed walk runs the same skill in batch mode, with a
scope-lock gate before any edit and agent-side reproduction per the `debug` protocols.

### Session environment recipe

Fast, honest sessions depend on the environment being set up deliberately:

- **Profile**: `bun run dev:prod` — docs (:3003), admin (:3002), client (:3001), and Storybook
  (:3004) against real Arbitrum One, the hosted indexer, and the production agent API.
  `dev:prod:mirror` adds a local indexer mirroring live chain. Health:
  `bun run dev:doctor -- --profile prod`.
- **Warm before dictating**: load each in-scope surface once. The client's boot watchdog shows
  recovery UI if React has not mounted within ~4.5s; a cold Vite transform can trip it, and a
  cold-load fallback is instrumentation, not a defect, until reproduced warm.
- **Watch for `new dependencies optimized`** in the dev log — that line means a dependency
  re-optimization full-reload just ate the current flow; note it and repair the
  `optimizeDeps.include` drift after the session.
- **Identity**: real steward identity via wallet connect in the authenticated Brave profile for
  write flows; `?mockAuth=deployer` for fast read-only inspection of real production data;
  `?mockAuth=steward` resolves to an address with no garden assignment and only proves the
  no-access gate. Mock auth changes the app's role context but does not disable transaction hooks:
  disconnect any wallet session before a mock-auth pass, and cancel any unexpected wallet prompt.
  The mock seam is
  **loopback-only and enforced in code**: it works solely on `localhost`/`127.0.0.1` — over
  `dev:tunnel` or any LAN/non-loopback host it is ignored and the real auth provider runs, so
  those checks go through authenticated Brave instead.
  `?presentation=pwa` once per tab for the PWA shell on desktop. **Passkey
  ceremonies cannot run on localhost** — the RP ID is `greengoods.app`, so passkey cases are
  `Blocked` locally by design and run against production installs instead.
- **Port ownership**: 3001/3002 are strict-port with no worktree offset — real-time fixes must
  land in the same checkout the founder is browsing, and surface leases
  (`bun run dev:stack status`) say who owns what. Never restart another session's stack.

## Agent execution protocol

This is the minimum protocol for agents performing a deep QA pass or validating user-facing work
— it applies inside qa-session fix windows and to any standalone agent verification.

### 1. Lock the journey and environment

Record the build or commit, surface, exact route, presentation mode, identity, role, locale, viewport,
theme, connectivity, and starting data state. If any of these materially changes the result, it is
part of the test case.

### 2. Reproduce from the rendered surface

Use authenticated Brave for profile-dependent local QA. Start with what a person can see and touch.
Do not infer that a provider, hook, or contract is the cause until the rendered surface is shown to
be intact.

### 3. Inspect geometry and interaction state

For suspect elements, inspect bounding boxes and computed `display`, `visibility`, `opacity`,
`pointer-events`, `overflow`, stacking, disabled state, selected classes, borders, rings, and text
contrast. Perform the interaction and verify that state actually changes.

### 4. Complete the critical path

Do not stop at route load or the first successful click. Continue through review, confirmation,
asynchronous progress, success, and the resulting destination. Exercise cancel and failure recovery
without discarding user input unexpectedly.

### 5. Sweep relevant states and siblings

Check the state matrix above and the directly related routes, roles, locales, or responsive layouts.
Keep the sweep bounded to the feature and its regression surface.

### 6. Anchor the regression

Add or identify the smallest deterministic check that would fail if the defect returned. Use unit or
component tests for logic, Storybook for controlled visual states, and route E2E for composition and
journey continuity. Do not use a synthetic shell as proof of a real route.

### 7. Produce a QA receipt

Every completed pass should leave this evidence:

```text
Build/commit:
Surface and route:
Presentation:
Identity and role:
Locale, theme, and viewport:
Starting data state:
Actions performed:
Expected result:
Actual result:
State matrix exercised:
Console/network observations:
Screenshot or DOM evidence:
Automated regression anchor:
Result: Pass | Fail | Blocked | Not applicable
Remaining risk:
```

A pass without this context is not reusable regression evidence.

## Defect writing standard

Write one defect per issue, in language a teammate can understand cold:

```text
[Surface] [route or journey] — [problem or blocked outcome]

Given [identity, role, locale, viewport, and data state],
when [action],
the product [actual visible or behavioral result].
It should [expected result].

Evidence: [screenshot, DOM measurement, error, or reproducible steps]
Regression anchor: [current test, missing test, or proposed deterministic proof]
```

Separate labels should distinguish:

- **Product defect** — the real rendered experience is wrong.
- **QA harness defect** — the test or fixture is nondeterministic, synthetic, stale, or misleading.
- **Missing proof** — the behavior may work, but no accepted evidence covers it.
- **Capability blocked** — the required browser, role, device, data, or service is unavailable.

one end-to-end experience acceptance contract.

## Improvement sequence

Implement improvements in this order so later signals are trustworthy.

1. **Restore client startup and recovery.** Add a route-level regression that fails when React never
   mounts, when the module graph cannot load, or when cache-busted reload returns to the same recovery
   state. Keep the friendly fallback tests, but distinguish “fallback displayed” from “recovery
   succeeded.”
2. **Make Storybook interaction CI deterministic.** Stories tagged `storybook-ci` must not contact
   live chain, IPFS, wallet, or Reown services. Add provider/query seams or remove the tag until the
   story has a controlled environment.
3. **Ship the human-led session loop first; defer the autonomous sweep.** Done: the `qa-session`
   skill owns the founder-led loop and orchestrates the existing debug, design, qa-triage, and
   validation authorities rather than duplicating them. The agent-led autonomous matrix sweep
   (`qa-sweep`) is deliberately deferred until items 1 and 2 are green — an autonomous sweep run
   today would re-report the boot watchdog and the red Storybook gate on every pass.
4. **Replace synthetic client coverage with real compositions.** Preserve useful shell fixtures, but
   add the actual PWA Home, Garden, Profile, work, commitment, proof, and offline flows. Replace public
   Fund, Impact, and Actions sentinels with deterministic real route components.
5. **Make selected visual and accessibility regressions blocking.** Start with the critical journeys
   in this document, approve stable baselines, fail unexpected diffs, and run axe checks against the
   same curated set. Do not multiply every story across every device.
6. **Add a role and device matrix to route E2E.** Prioritize steward, gardener, evaluator, and funder
   boundaries; iOS-sized and Android-sized PWA flows; and public pages at 375px and 1440px.
7. **Grow the catalog into a machine-readable journey manifest.** The seed exists:
   `scripts/data/qa-test-catalog.json` versions journeys with roles and states, and a planned
   `linkedChecks` field (not yet in the schema) is the growth path for mapping each case to its
   deterministic tests, stories, and most recent accepted evidence so coverage drift becomes
   visible.
8. **Repair QA-tooling drift.** The dev-port parser is fixed (self-checking, 2026-08-28). Still
   open: decide whether the validation selector needs an `audit` intent (none exists today) or
   document that audit-shaped work maps onto the existing `diagnose`/`review` intents.
9. **Add language-quality checks beyond key parity.** Exercise ICU pluralization, `Intl` date/number
   formatting, diacritics, long translations, and mixed user-authored content in the route where it
   is displayed.
10. **Documentation site QA lane.** Done at the definition level: docs is a first-class surface
    with its own journey matrix above and catalog cases `DOCS-001`–`DOCS-006` (navigation,
    search, glossary anchors, responsive shell, keyboard/focus, theme/diagrams). Still open:
    wiring any of it into CI beyond build success.

## Definition of QA complete

A frontend journey is QA-complete only when:

- its acceptance outcome is explicit;
- the real route has been exercised in the required presentation, role, locale, and viewport;
- primary actions are visible, understandable, reachable, and retain context across success or
  failure;
- applicable loading, empty, error, success, permission, long-content, and responsive states pass;
- keyboard, focus, accessible names, reduced motion, and target sizing have been checked;
- no blocking console, module-load, horizontal-overflow, clipping, invisible-text, or fixed-chrome
  collision remains;
- a deterministic regression anchor protects the behavior at the right layer;
- the QA receipt is attached to the change or issue; and
- unresolved risk and blocked capability are stated plainly.

Passing code checks is necessary. It is not, by itself, evidence that the product experience is
ready.
