# First Contribution

Green Goods is open-source infrastructure built by the
[Greenpill Dev Guild](https://paragraph.com/@greenpilldevguild), and contributions of any size are
welcome. A fixed typo teaches you the PR flow just as well as a feature does. This page walks the
whole path: finding something to work on, making the change, proving it, and getting it merged.

This page is the full contributor guide. The repository's
[CONTRIBUTING.md](https://github.com/greenpill-dev-guild/green-goods/blob/develop/CONTRIBUTING.md)
is its one-screen summary, kept next to the code.

## Find something to work on

Green Goods tracks its work in Linear, not GitHub issues; GitHub is for pull requests and code
review. That means the best first step is a conversation: say hello on
[Telegram](https://t.me/+N3o3_43iRec1Y2Jh) or [Discord](https://discord.gg/greenpill), tell us
what interests you, and a maintainer will point you at a scoped task that fits.

Two honest ground rules: confirm scope with a maintainer before investing serious time, and don't
treat unlabeled roadmap items as funded work. Green Goods doesn't run open-ended bounties; paid
implementation is grant-dependent and always scoped in writing first.

## Set up

If you haven't run the project yet, [Getting Started](./getting-started) takes 15 to 30 minutes
and ends with the app running on your machine. Come back here once you've seen it work.

## Bring an agent

Building with AI agents is a core part of how Green Goods gets made, not a side channel. The
maintainers develop with [Claude Code](https://claude.com/claude-code) and Codex daily, and the
repository is instrumented for it: an
[`AGENTS.md`](https://github.com/greenpill-dev-guild/green-goods/blob/develop/AGENTS.md) contract
at the root and in most packages, a [catalog of packaged skills](./agentic/skills) for common
workflows, and a validation selector that keeps agent-made changes honest.

The fastest start: open
[`ONBOARDING.md`](https://github.com/greenpill-dev-guild/green-goods/blob/develop/ONBOARDING.md)
and paste it into your agent. It's written to be read by one: your agent becomes an onboarding
buddy that checks your setup, picks the right path, and finishes with a short report of what it
verified, what's still missing, and which package owns your first task.

Agents get no shortcuts. Their changes pass the same review, the same CI Gate, and the same
[repo rules](https://github.com/greenpill-dev-guild/green-goods/blob/develop/CONTRIBUTING.md#repo-rules)
as anyone else's, and that's exactly why the practice works.

## Make the change

1. Branch from `develop`, named `<type>/<short-work-description>`. For example
   `fix/garden-join-toast` or `feature/assessment-export`. PRs target `develop`, the staging
   branch; maintainers promote to `main` in monthly releases.
2. Read the nearest `AGENTS.md` before editing a package. The root one maps the monorepo, and
   most packages carry their own with the rules that actually bite.
3. Keep the change inside the smallest package boundary that solves the problem, and add or
   update tests when behavior changes.

A few repo-wide rules worth knowing before your first diff: React hooks live in
`@green-goods/shared`, Ethereum addresses use the shared `Address` type, logging goes through the
shared `logger` (never `console.log`), user-facing strings ship in `en`, `es`, and `pt` together,
and there's exactly one `.env`, at the root. The full list lives in
[CONTRIBUTING.md § Repo Rules](https://github.com/greenpill-dev-guild/green-goods/blob/develop/CONTRIBUTING.md#repo-rules).

## Prove it

Ask the repository which checks your change actually needs; it picks the smallest honest set from
what you changed:

```bash
bun run check --plan -- --intent qa
```

Run the focused test that proves your change first, then the package checks the plan selects.
When you push, the pre-push hook runs the ready-for-CI gate for you. To run the same gate by hand,
name the test that proves your change:

```bash
bun run check -- --intent push --reuse-passing-receipts --test-path <package>:<test file>
```

CI covers broad regression across the repo, so you don't need to run everything locally. Two
habits help: always `bun run test`, never `bun test`, because the repo's test orchestration
depends on it; and `bun run format` fixes formatting, while `bun run format --check` only reports
it. For end-to-end or authentication changes, run the matching Playwright project from the
[Testing Guide](/builders/testing#commands-per-surface).

## Open the pull request

Open the PR into `develop` and say three things: what changed, why, and how you validated it.
Then expect some robot company:

- **CI Gate** is the required check. It aggregates every workflow your change triggered, and the
  PR merges only when it's green.
- **CodeRabbit and Codex review every push.** Respond to what's right, explain what isn't, and
  they re-review each time you push.
- Merging to `develop` deploys to staging. Your change reaches production with the next
  [monthly release](https://github.com/greenpill-dev-guild/green-goods/blob/develop/CONTRIBUTING.md#releases-and-hotfixes).
