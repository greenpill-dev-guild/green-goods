# Authentication

The client supports passkey-backed accounts and wallet-aware recovery through shared auth modules.
The implementation and provider configuration own ceremony details; this page explains the user
boundary.

## Flow

1. The client establishes the intended presentation and chain context.
2. Shared auth hooks start sign-in or registration with the configured relying party.
3. The resulting account/session becomes the identity used by application and transaction flows.
4. Recovery paths must preserve account continuity and make failure states explicit.

## Which sites a passkey works on

A browser offers a passkey only for the domain it was created under. Whoever issues the sign-up
options chooses that domain, so the passkey server decides where an account can sign in.

- **Green Goods passkey directory** (the agent route `/public/passkeys/rpc`): issues every passkey
  under `greengoods.app`, so one account signs in on every Green Goods site. A build uses it when
  `VITE_PASSKEY_DIRECTORY_URL` is set, and the agent serves it when `PASSKEY_DIRECTORY_ENABLED` is
  `true`.
- **Hosted passkey server**: issues each site its own hostname, so an account made there signs in
  only on the site that created it. Accounts made before the directory stay on it, and sign in the
  same way as before.

Sign-in asks the directory first and falls back to the hosted server for a name the directory does
not hold. The directory refuses a name the hosted server already holds, which keeps one owner per
name across both.

## Testing boundary

Passkey ceremonies depend on the configured relying-party domain and cannot be treated as proven by
localhost mocks. Use mocks for deterministic component and state tests; use the authenticated Brave
profile on the appropriate deployed origin for real ceremony proof. Never log credentials,
challenge material, wallet state, or session identifiers.
